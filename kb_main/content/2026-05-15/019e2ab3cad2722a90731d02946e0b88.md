# Domain Hints — 三层知识库

**Last updated**: 2026-05-01
**Current Round**: KDD Cup 2026 Round 1 prep (PCVRHyFormer baseline)

---

## Layer 1: Semantic Priors（跨 round 稳定）

### S1. Official schema truth: platform data is 120-column flat parquet
**Statement**: Official TencentGR / TAAC platform training data should be treated as the 120-column flat parquet schema. The 7-column nested format is a community/vendor adaptation layer, not the upstream truth. Any model, validator, or submission path that assumes nested `user_feature/item_feature/seq_feature` as canonical is suspect.

**Evidence**:
- Official Taiji baseline `dataset.py` consumes flat fid-suffixed columns directly: meta fields (`user_id`, `item_id`, `label_type`, `label_time`, `timestamp`), `user_int_feats_*`, `user_dense_feats_*`, `item_int_feats_*`, and `domain_a/b/c/d_seq*`.
- `feedback_data_schema_truth.md` records the 2026-04-29 verification that `data/demo_1000.parquet` and the TAAC sample mirror the flat schema expected by the platform baseline.
- Current project rule: vocab sizes from demo are lower bounds only; platform `run.sh` must regenerate schema/vocab against full `TRAIN_DATA_PATH`.

**Source experiments**: schema verification / official baseline inspection, `feedback_data_schema_truth.md`, `docs/data_split_finding_2026-04-30.md`

**Last verified**: 2026-04-29

### S2. Default rowgroup validation is in-distribution and cannot forecast leaderboard
**Statement**: The default platform/vendor validation split is optimistic. It samples the same training time window rather than a future temporal holdout, so `val_auc` is useful for overfit diagnostics but not sufficient for experiment decisions. Leaderboard AUC remains the ground truth for transfer.

**Evidence**:
- `pcvr_diag_data_split` showed all 1000 parquet shards share the same timestamp window; filename order is Spark repartition/coalesce output, not chronological partitioning.
- baseline-0 had local `val_auc` around 0.86 but leaderboard AUC only 0.81147, a gap of roughly 0.05.
- I-601 attempted `--split_mode timestamp`, but leaderboard fell from 0.81147 to 0.79927. This amended the earlier belief that timestamp split alone would recover the gap.

**Source experiments**: `docs/data_split_finding_2026-04-30.md`, `experiments/baseline_0_rankmixer/meta.md`, `experiments/I-601_timestamp_split/meta.md`, `feedback_val_split_is_misleading.md`

**Last verified**: 2026-05-01

### S3. Cold restart is load-bearing for high-cardinality ID regularization
**Statement**: Keep `--reinit_sparse_after_epoch=1` for PCVRHyFormer on TencentGR unless explicitly testing cold restart itself. It is not defensive boilerplate; it is a primary regularizer against high-cardinality ID memorization and dense-parameter over-reliance on transient ID channels.

**Evidence**:
- I-503 disabled cold restart with `--reinit_sparse_after_epoch 999`; leaderboard dropped from baseline-0 0.81147 to 0.79771 (`-0.01376`).
- I-503 validation degraded rapidly after epoch 1: val loss rose from about 0.22 to 0.62 by epoch 4, consistent with overfitting after IDs have been touched once.
- Split diagnostics explain the mechanism: user IDs are non-recurring, item overlap is very low, and conversion rate drift across the observed window is severe. ID memorization does not transfer.

**Source experiments**: `experiments/baseline_0_rankmixer/meta.md`, `experiments/I-503_no_cold_restart/meta.md`, `feedback_cold_restart_load_bearing.md`, `docs/data_split_finding_2026-04-30.md`

**Last verified**: 2026-05-01

### S4. Capacity-first experiments are risky under current distribution shift
**Statement**: Adding trainable high-cardinality embedding capacity or larger model components is unlikely to close the leaderboard gap by itself, and can waste quota through overfit or OOM. Distribution-shift controls should be challenged before capacity increases.

**Evidence**:
- High-cardinality sequence vocab sizes include 64.7M and 86.3M tables; unlocking all major tables would require far beyond the platform memory budget when weights, gradients, and optimizer state are counted.
- The `feedback_codex_challenge_before_experiments.md` review caught that `emb_skip_threshold=0` was both memory-risky and conceptually misaligned with a val/test distribution-shift gap.
- baseline-0 already overfits the local validation/leaderboard relationship; more capacity would likely improve in-window validation before proving transfer.

**Source experiments**: `docs/data_split_finding_2026-04-30.md`, `feedback_codex_challenge_before_experiments.md`, baseline-0 val/leaderboard gap

**Last verified**: 2026-04-30

## Layer 2: Episodic Priors（本 round 多次确认）

### E1. baseline-0 RankMixer remains the current leaderboard reference
**Statement**: Among the four completed/recorded platform evaluations, baseline-0 is still the best leaderboard reference at 0.81147. New deltas should be compared against the correct sibling experiment, but final improvement claims must still clear baseline-0 unless intentionally optimizing a different base.

**Evidence**:
- baseline-0: 0.81147 leaderboard AUC, inference 323.61s, best submitted checkpoint epoch 6.
- I-503 cold restart off: 0.79771 (`-0.01376` vs baseline-0).
- I-601 timestamp split: 0.79927 (`-0.01220` vs baseline-0).
- I-602 timestamp split + id_dropout: 0.80366 (`-0.00781` vs baseline-0).

**Source experiments**: baseline-0, I-503, I-601, I-602, `eval_Logs/summary_2026-05-01.md`

**Last verified**: 2026-05-01

### E2. Experiment interpretation must use sibling comparators
**Statement**: When an experiment inherits another experiment's infrastructure change, judge the isolated variable against that sibling base first, then separately judge the combined package against baseline-0. Otherwise, a positive isolated effect can be mislabeled as negative, or a negative base can hide a useful component.

**Evidence**:
- I-602 is negative vs baseline-0 (`0.80366 - 0.81147 = -0.00781`) but positive vs I-601 (`0.80366 - 0.79927 = +0.00439`) because both share `--split_mode timestamp`.
- `eval_Logs/summary_2026-05-01.md` explicitly identifies I-601 as the apples-to-apples comparator for I-602.

**Source experiments**: I-601, I-602, `eval_Logs/summary_2026-05-01.md`

**Last verified**: 2026-05-01

### E3. Timestamp split as currently implemented is not an approved validation fix
**Statement**: `--split_mode timestamp` should not be treated as a solved validation repair. It produced a leaderboard regression and may introduce best-epoch drift or a thin-slice validation artifact.

**Evidence**:
- I-601 expected roughly no leaderboard change but returned 0.79927, `-0.01220` vs baseline-0.
- I-601 selected a later checkpoint around epoch 8, while baseline-0's best submitted checkpoint was epoch 6. With per-epoch cold restart, later checkpoints can be worse on leaderboard despite better local validation.
- The original timestamp-split premise was amended: files are sample-shuffled, but within-window timestamp gradient may still be meaningful.

**Source experiments**: I-601, baseline-0, `docs/data_split_finding_2026-04-30.md`, `eval_Logs/summary_2026-05-01.md`

**Last verified**: 2026-05-01

## Layer 3: Working Observations（单实验，待晋升）

### W1. id_dropout effect is null on clean baseline (INVALIDATED 2026-05-01 by I-603)
**Original observation**: I-602 improved leaderboard AUC from I-601's 0.79927 to 0.80366 (`+0.00439`) while sharing the same timestamp-split base.

**Invalidation**: I-603 ran id_dropout p=0.3 t=10K on baseline-0 base (no timestamp_split) and got 0.80956, **-0.00191 vs baseline-0** (neutral, in noise band). The I-602 +0.0044 was timestamp_split partial-fix masquerading as +EV, not a real id_dropout effect.

**Source**: `experiments/I-603_id_dropout_clean_baseline_base/meta.md`, `eval_Logs/i-603.md`

**Conclusion**: id_dropout at p=0.3 t=10K is dead on baseline-0. Do not propose id_dropout p sweeps (p=0.1, p=0.5) or threshold sweeps (t=1K) on this lever — they are likely also null. **Pivot to feature engineering (I-605 seq-time, I-608 item_id token).**

**Confirmed prior**: Sibling-comparator rule (E2) is critical but insufficient — the comparator itself must NOT be a degraded base. I-601 was -0.012 vs baseline, so any "+EV vs I-601" claim should have been re-tested vs baseline-0 directly before treating as positive.

### W2. I-602 inference time improvement is probably platform variance
**Observation**: I-602 inference time was 211.64s vs baseline-0 323.61s and I-601 320.82s.

**Source**: `eval_Logs/summary_2026-05-01.md`

**Caveat**: id_dropout is training-only and the inference path is byte-identical, so this should not be treated as a model-speed gain.

**Prerequisite before promotion**: Repeated evals with identical inference code showing stable lower latency, or code-level evidence that inference changed. Current evidence is insufficient.

### W3. timestamp split may harm through best-epoch drift
**Observation**: I-601 used a later checkpoint around epoch 8 and underperformed baseline-0's epoch-6 checkpoint by `-0.01220`. Because cold restart resets sparse embeddings each epoch, later epochs may be less favorable on leaderboard even if timestamp validation prefers them.

**Source**: I-601, baseline-0, `eval_Logs/summary_2026-05-01.md`

**Caveat**: This is one explanation, not proven root cause. The alternative explanation is that the timestamp tail is itself a thin and overfit-prone validation slice.

**Prerequisite before promotion**: Evaluate matched checkpoints across baseline-0/I-601 or run a controlled timestamp-split rerun that decouples split mode from checkpoint choice.

### W4. Capacity is NOT the leaderboard bottleneck (CONFIRMED 2026-05-02 by I-604)
**Original observation**: Diagnostics suggested distribution-shift was the gap driver, with capacity as secondary. We tested whether adding model depth could close the gap.

**Confirmation**: I-604 ran `--num_hyformer_blocks 2->3` (single-flag capacity probe) on baseline-0 base. Result: **0.80569 leaderboard, -0.00578 vs baseline-0** AND **509s inference time vs baseline 323s (+57%)**. Both AUC and latency hurt.

**Source**: `experiments/I-604_layer3_capacity_probe/meta.md`, `eval_Logs/i-604.md`

**Conclusion**: Adding capacity (depth) does NOT help on baseline-0. Likely overfits the in-window training data more without improving transfer. Combined with I-603 (regularization neutral), Wave 1's two main hypothesis paths — regularization and capacity — are both empirically confirmed dead. Only feature engineering and loss/training changes remain as viable directions.

**Promote to Episodic candidate**: This is the second consistent finding (I-503 cold-restart-off + I-604 layer-up both hurt AUC), suggests "TencentGR-CVR's leaderboard gap is structural — neither regularization nor capacity moves it. Feature engineering or loss redesign is required."

### W5. amp + torch.compile saves ~45% epoch time with -0.003 AUC tradeoff (CONFIRMED 2026-05-02 by I-606)
**Observation**: I-606 = baseline-0 + amp(bf16 autocast) + torch.compile(mode='default'). Result: leaderboard 0.808328 (-0.00314 vs baseline), but epoch 1 took 33.5 min vs baseline ~60 min (~45% speedup). Cold restart preserved (97 reset, 1 kept).

**Source**: `experiments/I-606_engineering_speedup/meta.md`, `eval_Logs/i-606.md`

**Decision**: PROMOTE as fork base for all future experiments. The -0.003 AUC is borderline (right at noise band), but the 1.45x training speedup is multiplicative on every future experiment. All Wave 2+ packages fork from `experiments/I-606_engineering_speedup/code/` instead of `experiments/baseline_0_rankmixer/code/`.

**Caveat**: Future fork experiments showing AUC drop > 0.005 vs expected must run a `--no_use_amp --no_use_compile` control before blaming the new feature.

### W6. Dense projection on seq-internal time signal works; high-card sparse new embeddings do not (CONFIRMED 2026-05-02 by I-605 vs I-608)
**Observation**: Two parallel Wave 2 feature engineering experiments produced opposite outcomes:
- **I-605** added 4 frequencies of Fourier (1h/6h/24h/7d) + recency log+bucket = 16 dense dims per seq token, projected via `Linear(16, d_model)` per domain (+4,352 params). Result: leaderboard **0.81730 (+0.00583 vs baseline-0)**, FIRST breakthrough across 9 experiments.
- **I-608** added a new sparse Embedding for `item_id` hashed to 1M buckets (+67M params), entered cold-restart reset pool. Val_auc 0.8637 (highest seen) BUT leaderboard **0.808031 (-0.00344 vs baseline-0, +0.0 vs I-606)** — net zero contribution.

**Source**: `experiments/I-605_seqtime_fourier_recency/meta.md`, `experiments/I-608_item_id_token/meta.md`, `eval_Logs/i-605.md`, `eval_Logs/i-608.md`.

**Mechanism understanding**:
- Dense projections enforce smoothness across the train→test distribution shift (item_id D9-vs-D0 overlap = 1.8%). The 16-dim Fourier+recency signal exists for ALL events regardless of train vs test, so the projection learned at training time keeps mapping correctly at test time.
- High-cardinality sparse embeddings, even with cold restart, can only memorize per-ID patterns. With 1.8% train→test ID overlap, the embeddings learned at training time are largely useless at test time — and the high val_auc 0.8637 was train memorization (val IS in-distribution due to rowgroup split).

**Decision**: PROMOTE I-605 as new fork base for all Wave 3 experiments. Wave 3 dense feature engineering candidates (I-615 frequency sweep, I-624 Target-Aware item pooling, I-625 inter-event gap, I-610 HeadMixing on query) all use dense projections. **Sparse capacity additions for ID-like features are an anti-pattern on TencentGR.**

**Promote to Episodic candidate**: This is the strongest empirical signal we have on the regularization-vs-capacity-vs-feature triangle. Should be rewritten as Episodic prior after I-615 confirms direction holds across frequency sweep.

### W5. Vendor/platform baseline should not receive speculative compatibility patches
**Observation**: Local Windows compatibility changes to vendored platform files can break Taiji even when local smoke tests pass. Vendor edits should require observed platform failure and documented root cause.

**Source**: `feedback_no_speculative_vendor_patches.md`

**Caveat**: This is an engineering-process prior, not a modeling prior.

**Prerequisite before promotion**: Keep as a guardrail unless a future platform/API change forces intentional vendor divergence with evidence.
