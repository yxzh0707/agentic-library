# Data Split Finding — 2026-04-30

> Source: diagnostic Job `pcvr_diag_data_split` run on Taiji platform 14:11.
> Raw logs: `pcvr_diag_data_split_output.md` (root, gitignored if oversized — keep this analysis as the durable record).

## TL;DR

`dataset.py:get_pcvr_data` splits train/val by alphabetical file-name order. We previously assumed this would correspond to time-ordered file partitioning, making val "the most recent 10%" and a reasonable proxy for test. **The diagnostic disproves that assumption.**

The actual TencentGR layout: 1000 parquet shards, all named `part-00000-<uuid>-c000.gz.parquet` ... `part-00999-<uuid>-c000.gz.parquet`, each containing a **random sample of the same ~3.3 day time window** (Spark `coalesce`/`repartition` output). All files share an identical timestamp range; there is no temporal monotonicity across file index.

Therefore:
- val = a uniformly-random 10% sample of the same 3.3-day training period
- val_auc 0.86 is in-distribution validation, not a forecast of test_auc
- The 0.05 gap between val (0.86) and leaderboard (0.81) is **train→test distribution shift**, almost certainly driven by the platform-held test set being a different (likely later) time period

Local val_auc is therefore an **optimistic, in-distribution metric**. Improvements on it can transfer to leaderboard or not, depending on whether they actually attack the distribution shift.

## Evidence

### File naming
1000 files all of pattern: `part-NNNNN-e514e21a-e5a7-465a-9346-3cd81c8da444-c000.gz.parquet`. Single shared UUID across all parts indicates one-time `coalesce(1000)` write, not a daily ETL.

Conclusion: every file independently spans the full window. Files are sample-shuffled, not time-partitioned.

### High-cardinality seq features (vocab > 1M)

| Domain | fid | vocab_size  | weight memory at fp32, dim=64 |
|--------|----:|------------:|------------------------------:|
| seq_b  |  69 |  64,710,562 | **15.4 GB**                   |
| seq_c  |  29 |   5,764,358 | 1.40 GB                       |
| seq_c  |  34 |   1,031,305 | 0.25 GB                       |
| seq_c  |  47 |  86,335,515 | **20.6 GB**                   |

Adding Adagrad state and gradient triples each value. Total if all four are unlocked: **≈ 113 GB** — far beyond the 19 GiB per-task slot. `--emb_skip_threshold 0` is therefore guaranteed-OOM and was never a viable experiment.

Feasible thresholds:
- threshold = 10,000,000 → unlock fid 29 + 34 only → ≈ 5 GB increment
- threshold = 2,000,000 → unlock fid 34 only → ≈ 0.75 GB increment
- threshold = 50,000,000 → also unlocks fid 69 → OOM

Fids 69 (seq_b, vocab 64.7M) and 47 (seq_c, vocab 86.3M) are the two giants — almost certainly `item_id` and `content_id`/`creative_id`.

## Strategic implications

### What this overturns

- "Add capacity" experiments (I-301 DHEN, I-201 HeadMixing, larger d_model) are still valid for raw model power but **will not narrow the val→leaderboard gap by themselves** — capacity gains tend to overfit harder to the train period.
- Reading val_auc as a forecast of leaderboard delta is unreliable. Two experiments with similar val_auc may diverge by 0.01+ on leaderboard depending on how they handle distribution shift.
- I-502 with threshold = 0 was OOM-doomed from the start. Even threshold = 10M would unlock only the two smaller IDs, leaving the two giants zero-vectored.

### What this elevates

- **Time-aware validation split** becomes the most valuable single change we can make. With per-row `timestamp` available in every parquet, we can split val from the temporal tail of the data instead of by file name. This realigns local val with what the leaderboard actually measures.
- High-cardinality embedding regularization (dropout, L2, random-drop on the two giant IDs at train time) attacks the overfit-to-train-period problem head-on.
- Calibration may matter more than expected once the gap mechanism is "predicted probability for unseen IDs is miscalibrated".

### What this does to in-flight I-503

I-503 (`--reinit_sparse_after_epoch 999`, disable cold restart) is currently training. Pre-finding hypothesis: cold restart is over-regularizing → disabling it should help. Post-finding hypothesis: cold restart was actually a useful regularizer against distribution shift → disabling it may **lower** leaderboard AUC. Either outcome is informative; do not stop the run, just adjust expectations.
