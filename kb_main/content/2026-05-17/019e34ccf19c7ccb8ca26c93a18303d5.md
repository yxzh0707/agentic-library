# Data audit — label_type schema + action_time semantics

- **Run**: 2026-05-14 ~12:00 BJT
- **Trigger**: post-Codex Gate A discussion; need to verify whether IF-DFM / Tri-BCE / ESMM-style multi-task are applicable before designing the next experiment.
- **Stage**: protocol-driven-execution Stage 2 (validation)

## Q1 — Does `label_type==0` exist in production training data?

### Evidence (independent sources)

| # | Source | Finding |
|---|---|---|
| 1 | `experiments/I-670_mldcn_stable_cross/code/dataset.py:645` | `labels = (batch.column('label_type').fill_null(0).to_numpy(...) == 2)` — reads label_type, does NOT filter rows |
| 2 | Same file lines 153, 185 | Doc string says "label_type == 2" → binary; no filter on 0 |
| 3 | `item_heat.py:162-165` | `n_exp = len(label_types); n_click = (label_types >= 1).sum(); global_ctr = n_click / n_exp` |
| 4 | Training logs across **9 independent jobs** (I-635 cate version, I-635 item version, I-651, I-643, I-670 etc., dates 5/5 – 5/12) all report `global_ctr=1.0000, global_cvr=0.0959` | If any row had `label_type==0`, global_ctr would be < 1.0 |
| 5 | `vendor/TAAC_2026/README.md:127` example shows `seq` field with action_type values 1, 2, 3, 4 — but **no 0** | Suggests action_type 0 is not in upstream data |
| 6 | `docs/data_understanding_v2.md` ("demo_1000 缺 label_type==0 行") | Explicit doc statement that demo_1000 has no 0 rows |
| 7 | `docs/domain_hints.md:14` lists meta columns: `user_id, item_id, label_type, label_time, timestamp` — no separate "is_clicked" column | Confirms training data is filtered to clicked-only at upstream pipeline level |

### Verdict
**✅ CONFIRMED — `label_type==0` does NOT exist in production training data.**

Mechanism: training data is at the **post-click** granularity — already filtered to "user clicked the item" events upstream. label_type ∈ {1, 2} only:
- `label_type==1`: clicked, did not convert (~90.4% of rows)
- `label_type==2`: clicked, did convert (~9.6% of rows)

This is canonical **PCVR = P(conversion | click)** training setup.

### Implication on previously-considered options
| Option | Status post-Q1 |
|---|---|
| Tri-BCE (label 0/1/2 three-task) | ❌ DEAD — class 0 absent |
| ESMM (pCTR + pCVR shared trunk) | ❌ DEAD — click is trivially 1.0 |

## Q2 — `label.action_time` semantics on `label_type==1` samples

### Schema recap
From `docs/data_eda_summary.md` + `vendor/TAAC_2026/README.md:127`:
- Top-level `label` is `list<element: struct<action_time: int64, action_type: int64>>`
- Each list entry is an event with its own timestamp + action_type
- Top-level `timestamp` (int64) is the sample-level impression/click time
- Top-level `label_time` (per `docs/domain_hints.md:14`) is a flat meta column — likely derived from earliest action_time

### How current pipeline uses these fields

| Field | Current usage | Citation |
|---|---|---|
| `timestamp` (sample) | Used by item_heat for window calculation; gap-features for seq | `item_heat.py:151`, `dataset.py:572,592` |
| `label_type` (sample) | Reduced to binary `==2` | `dataset.py:645-646` |
| `label_time` (sample) | Listed in meta but **not consumed by dataset.py** | `domain_hints.md:14` |
| `label.action_time` (list-element) | **NOT consumed** by `dataset.py` or vendor `data.py` | `vendor/.../hyformer/data.py:592` only reads `action_type`, ignores `action_time` |

### Inferred semantics

For `label_type==1` (clicked, not converted):
- Label list contains at least one entry with action_type==1 (the click event itself), action_time = click timestamp
- May contain other action_types (3 = ?, 4 = ?) — vendor example shows action_types 1/2/3/4 used in `seq` field; same set probably valid in `label` list
- No action_type==2 entry → final binary label = 0

For `label_type==2` (clicked, converted):
- Label list contains BOTH (t_click, 1) AND (t_conv, 2)
- `delay = t_conv - t_click` is measurable and likely valuable

### Verdict
**✅ CONFIRMED — `label.action_time` exists and is meaningful but completely unused.**

Specifically:
- **Per-event timing within each label list IS available** (action_time int64)
- **Current dataset.py + vendor data.py both ignore action_time** — only action_type is consumed for the binary label reduction
- For `label_type==2` samples: click→conversion **delay** can be computed
- For `label_type==1` samples: only click time, conversion did not happen by data-snapshot time → right-censored

### Implication on previously-considered options
| Option | Status post-Q2 |
|---|---|
| **IF-DFM (influence-function delayed feedback)** | ✅ **APPLICABLE** — action_time per event + 4× CVR drift D0→D9 = paper's exact setup. Right-censored unconverted samples are also paper's standard formulation. |
| **TRACE (post-click trajectories)** | 🟡 **PARTIALLY APPLICABLE** — label list contains post-click events with timing, so retrospective trajectory completion can be implemented. But "trajectory" in TRACE means user behavior AFTER click; our label list seems to be **target-item-specific events** (click + conv on the same item), not general post-click behavior. Need to verify if the label list contains non-target post-click events (action_types 3, 4 on other items) or only target-item events. |
| **Day-bucket reweighting (IF-DFM-Lite)** | ✅ APPLICABLE — sample-level timestamp is available; can bucket samples by training day and reweight by similarity to test period CVR distribution |

## Outstanding follow-ups

1. **Verify label list contents for label_type==1 samples**: does it contain non-target post-click events (action_types 3 or 4 on different items) or only target-item events? Answer determines if TRACE is applicable.
2. **Confirm `label_time` semantics**: is it the click time or conversion time? Whether it's derived from action_time list or independently populated upstream.
3. **Measure per-day sample distribution**: is D0:D9 sample ratio balanced 10% each, or skewed? Affects day-bucket reweighting design.

These outstanding items don't block decision but would refine implementation. They can be answered by a single small probe job that prints EDA on label-list contents.
