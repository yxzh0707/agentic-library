# Current Strategy

Last updated: 2026-04-16

## Phase
**Framework Round 1 Ready** — 等正式数据（4/24），不再做 demo 实验

## 核心结论（Day 1-5 积累）

### 架构
- **主线**: UniRec-Hybrid（无 GLN）
  - Target-aware pooling + HeadMixing + Per-token FFN
  - 2 层 HybridBlock，D=128，H=4
- **备线**: vendor UniRec（公平排名第一，0.7596）
- 所有 demo 实验结论标记为 **provisional**（1000 样本噪声 ±5.7%）

### 已验证的组件（需正式数据重验）
| 组件 | Demo 结论 | 置信度 |
|------|-----------|--------|
| HeadMixing | 关键（-8.5%）| 中 — 勉强超噪声 |
| Target-Aware Pooling | 重要（-7.8%）| 中 — 勉强超噪声 |
| Per-token FFN | 有帮助（-4.7%）| 低 — 在噪声内 |
| GLN | 有害（+0.4%）| 低 — 在噪声内 |
| NAL | 无效（-2.7%）| 低 — 可能因数据太小 |
| Self-Attention | 过拟合（-5.2%）| 低 — 可能因数据太小 |

### 数据管线
- 原生 flat reader 读官方 120 列格式
- Schema validator 可 10 分钟内验证 Round 1 兼容性
- max_seq_len=128（demo 序列最长 2394，截断丢信息严重，Round 1 需调优）
- dense_pad_dim=768（demo 实际 736 维）

## 暗室碰撞实验校准结果（2026-04-16）

> 来源：`historical_sandbox/meta/summary.md`（3 轮 61/90）
> 以下 9 条 Process Corrections 在 Round 1 正式数据到达后强制执行。

### 高置信（直接应用）
1. **特征事前统计分析**：构造特征 → 与 label 相关性/覆盖率/分布分析 → 决定是否入模（不再"构造完直接扔进模型"）
2. **范式迁移检查**：Phase 1 定向时必须先问"这个 CVR 任务能否被重定义为已解决的问题？"
3. **多视角融合在单模型内部**：UniRec-Hybrid 的 target-aware pooling + HeadMixing 已是 2 个视角，评估是否需要更多（multi-branch/multi-head）
4. **Process rule 根据数据规模调整**：数据 <100K 时数据优先，>100K 时数据与架构可并行

### 中置信（Round 1 数据验证后确认）
5. **数据清洗注意力 40%**：但 >1M 时可并行推进架构选型
6. **选对方向后内部精细化**：确定 UniRec-Hybrid 为主线后，竞争力来自 target-aware pooling / HeadMixing / Per-token FFN 的精细调优，不是换架构
7. **序列建模考虑多层级**：如果 Round 1 数据有 session 结构，考虑 item → session → user 层级建模

### 待定
8. **预训练**：数据量 >10K 时考虑对 UniRec-Hybrid 做预训练（MLM 或对比学习）
9. **图结构**：如果数据有多模态特征，图结构可能有独特价值（不要因成本高就过早淘汰）

### 应丢弃的错误先验
- ~~"先构造全部特征再扔进模型"~~ → 事前分析后筛选
- ~~"数据先行 always 优于架构先行"~~ → 规模大时可并行
- ~~"成本高的方案应优先淘汰"~~ → 延迟淘汰到有数据支撑时

## Round 1 执行计划（4/24 起）

### 第一天（4/24）
- T+0~10min: Schema 验证
- T+10~25min: **EDA + 特征事前分析**（模态贡献/label 相关性/分布 → 筛选） ← 暗室校准
- T+20min: **范式迁移检查**（"这个 CVR 任务能否重定义？"） ← 暗室校准
- T+25~50min: 3-seed baseline
- T+50~60min: 首次提交
- T+60min~: 分析 leaderboard 排名，规划迭代方向

### 第二天起
- 基于正式数据 AUC 做可信 ablation（3-seed 强制）
- 按 leaderboard 反馈调整优先级
- 触发算法评审协议做架构决策

## 迭代优先级（按预期收益排序，含暗室校准修正）
0. **数据 EDA + 特征事前分析** ← 暗室校准 Rule 1（如数据 >100K 可与 1 并行）
1. max_seq_len 调优（128 → 256/512）
2. 学习率 schedule（cosine decay + warmup）
3. batch_size 调优
4. **UniRec-Hybrid 内部精细化**（target-aware/HeadMixing/Per-token FFN 调优） ← 暗室校准 Rule 6
5. 组件 ablation 重验（3-seed）
6. NAL 重试（INFO-NCE 90pos/20neg 配方） ← 论文研究修正
7. **Session-level 建模**（如果数据有 session 结构） ← 暗室校准 Rule 7
8. **预训练**（如果数据量 >10K） ← 暗室校准 Rule 8
9. 序列压缩方案（SimHash 采样 vs truncate vs learned） ← 论文研究

## 只做 3 件事（最低保证）
1. 正式数据接入 + 首次提交
2. 3-seed 可信 ablation → 确定最终架构
3. 超参调优 → 榨取最后几个 AUC 点

## Do NOT Explore
- Ensemble（禁止）
- 从零设计全新架构（基于 UniRec-Hybrid 迭代）
- 在 demo 数据上继续实验
- 重型 HPO（除非正式数据量足够大）

## 关键风险
1. 正式数据 schema 变化导致 reader 不兼容（有 validator 兜底）
2. 正式数据量太大导致训练慢（需调 batch_size / 序列截断策略）
3. 1000 样本的架构结论全部不成立（需重建所有置信度）
