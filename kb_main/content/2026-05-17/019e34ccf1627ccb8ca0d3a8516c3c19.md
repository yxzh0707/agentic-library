## Config delta vs baseline-0

```
+ --id_dropout_prob 0.3
+ --id_dropout_threshold 10000
```

That's it. **No timestamp_split.** All other flags byte-identical to baseline-0's run.sh.

`dataset.py` and `train.py` are inherited from I-602 (which already include the new
constructor kwargs for both `timestamp_*` and `id_dropout_*`); but with `--split_mode`
unset, the default `rowgroup` branch executes and timestamp filtering is bypassed
entirely. Net effect: identical to baseline-0 except per-row id_dropout in training.

## Why this experiment

I-602 had **two** changes vs baseline-0: timestamp_split (from I-601 inheritance) +
id_dropout. Result: -0.008 vs baseline-0, but +0.0044 vs I-601. The +0.0044 is the
only positive signal we have, but it's confounded by sitting on a -0.012 base.

I-603 strips timestamp_split out, leaving id_dropout as the **single** delta vs
baseline-0. Result is directly comparable to 0.81147.

| Comparator | Provides |
|---|---|
| I-603 vs baseline-0 | clean isolated id_dropout effect |
| I-603 vs I-602 | tells us how much of I-602's -0.008 was timestamp_split's fault |

## Mechanism (per Codex review of I-602)

Cold restart already wipes high-cardinality Embeddings every epoch end
(`--reinit_sparse_after_epoch=1` is load-bearing per I-503). So id_dropout's primary
target is **NOT** sparse-Embedding memorization but **dense-parameter co-adaptation
to the ID channel**: attention, projection, MLP, head weights persist across
epochs and can learn to lean on per-row IDs even after Embeddings reset. Forcing
30% of rows to have zeroed IDs trains those dense weights to function without
that signal.
