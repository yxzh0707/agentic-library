# I-640_token_dropout

```yaml
id: I-640
name: token_dropout
status: ready_for_taiji
base: experiments/I-625_gap_features/code/
fork_base: "experiments/I-625_gap_features/code/"
trigger_log:
  - 2026-05-05 17:00: Loss-axis closure (I-632/I-632b KILLED) -> regularization
    axis becomes a viable parallel track alongside I-635 feature axis.
  - 2026-05-05 19:00: Forum 0.8238 stack analysis identified "单独给用户和历史
    序列 token 的 dropout" (separate dropout for user / history seq tokens) as
    one of three ingredients. Forum-validated by 旧梦's LB jump.
prior:
  expected_lb_auc: 0.823
  range: [0.821, 0.825]
  p_improve_over_baseline: 0.30  # forum-validated but mechanism is generic
  baseline_lb_auc: 0.822863  # I-625

amp_compile_caveat: "Inherited from I-625 (amp+compile always on)"

rationale:
  - Loss-axis closed (4/4 KILL: focal + pairwise). Feature-axis (I-635) is
    P0 in the other Taiji slot. This experiment fills the regularization
    axis — orthogonal to both closed-loss and new-feature directions.
  - Forum competitor reported "+EV" attributing it to per-token (not per-
    feature) dropout applied to user-side and history-seq tokens
    independently. Mechanism: each token has small probability p of being
    fully zeroed during training, forcing the transformer to not over-rely
    on any single token (analogous to layer-wise dropout in BERT or token
    masking in MAE).
  - Distinct from I-603 id_dropout (KILL). I-603 dropped individual sparse
    id features within a single token's input embedding. I-640 drops the
    WHOLE token after projection — a coarser, structure-level regularizer.

design:
  user_token_dropout_p: 0.05  # applied to user_ns and user_dense_tok rows
  seq_token_dropout_p: 0.05   # applied per-position per-domain in seq_tokens
  applies_only_in_training: true
  inverted_dropout: true  # x * mask / keep_prob, preserves expected value

  scope:
    user_ns: yes (drop whole user_ns rows of (B, num_user_groups, D))
    user_dense: yes (drop the single (B, 1, D) user_dense_tok)
    item_ns: NO (item-side stays — fewer item tokens, higher signal density)
    item_dense: NO (same reason)
    seq_tokens: yes (per-position drop on (B, num_feats, max_len) seq tokens
                     across each domain a/b/c/d)

  not_applied_to:
    seq_time_feats: untouched
    output_proj: untouched
    classifier: untouched

new_dense_params: 0  # pure forward-time stochastic regularization

decision_thresholds:
  promote_if: "leaderboard_auc >= 0.825"
  neutral: "0.821 <= leaderboard_auc < 0.825"
  kill_if: "leaderboard_auc < 0.821"

next_actions:
  promote:
    - Stack with I-635 winner (if any) — regularization composes with new feat.
    - Sweep p ∈ {0.025, 0.05, 0.10} to find optimum.
  neutral:
    - Try p=0.10 (more aggressive); or split rate (user=0.05, seq=0.10).
    - Consider I-639 context-gating as alternative regularization.
  kill:
    - Token-level dropout doesn't transfer in our regime (despite forum signal).
    - Either forum's gain came from a different mechanism, OR our base
      (I-625 with cold restart) already absorbs the regularization budget.

implementation_notes:
  - model.py forward(): after ns_parts assembly, apply Bernoulli mask to
    user_ns and user_dense_tok before concat. After per-domain seq_tokens
    embedding, apply Bernoulli mask to (B, num_feats, max_len) seq token
    tensor. Both gated by self.training.
  - predict() path bypasses dropout (eval mode never drops).
  - Padding positions are already 0 in seq tokens; dropout × 0 = 0, harmless.
  - Inverted dropout (divide by keep_prob) preserves expected magnitude so
    no train/eval scale mismatch.

architecture_constraint:
  - I-625 base: T = num_queries*num_sequences + num_ns = 2*4 + 8 = 16,
    64 % 16 = 0 ✓. I-640 does NOT add a new token, so num_ns stays at 8.
    No --user_ns_tokens change required (unlike I-635).
```
