# I-671 — Cate × Time Second-Order Cross Feature

## Hypothesis

Combining two project-PROMOTED axes with an **explicit pairwise feature cross**:
- **I-643 cate-OOF heat** (`item_int_feats_84` cate-level CTR/CVR, 15 dims dense, OOV-safe via cate-sharing) — LB +0.00175
- **I-625 gap features** (8 Fourier dims of `abs(ts[i]-ts[i-1])` inter-event gap, projected per-domain) — LB +0.011 (project's biggest single PROMOTE)

A second-order cross between these two **stable + transferable** signals captures: *given an item's category-level conversion propensity, modulated by the user's temporal activity pattern* — neither side is id-dependent, so should transfer to OOV.

## Why this is NOT a closed-axis repeat

- I-651 multi-cate KILL was multiple cate features **on the same cate axis** (stacking similar signals). I-671 is **cate × time** across two **distinct** axes. Structurally different.
- I-654 (cate-OOF + dow stack) NEUTRAL but no cross — pure additive. This is the cross.
- I-639 time-feat context gating KILL was **gating** time features by context. I-671 is **cross**, not gating — no multiplicative scaling that creates train-period correlations.

## Architecture spec

### Module: `CateTimeCross`

Inputs at each forward pass (per-row):
- `cate_heat`: 15-dim dense vector — the existing I-643 `events_artifact` lookup output for the target item's cate (already computed upstream in dataset.py)
- `time_context`: aggregated 8-dim temporal context vector derived from the user's recent gap features

Output: a `d_cross = 32` dim dense vector

### Compute time_context

Codex chooses ONE of these (in preference order, fall back if higher-EV option unavailable):

**Preferred (simpler)**: extract the **most recent valid timestep's** `seq_time_feats` from the user's strongest domain (domain_a is preferred per project history; fall back to the domain with the longest valid sequence in the row). The last-timestep slice is 8 dims (the gap-Fourier portion). This is `time_context`.

**Fallback if last-timestep extraction is too fragile**: mean over last K=4 valid timesteps from `seq_time_feats`. Still 8 dims.

Either path is OK — Codex picks. Document choice in IMPLEMENTATION_PLAN.md.

### Forward steps

1. `cate_heat`: (B, 15)
2. `time_context`: (B, 8) per above
3. Compute outer product / bilinear cross:
   - Option A (full outer): `cross_2d = cate_heat.unsqueeze(2) * time_context.unsqueeze(1)` → (B, 15, 8) → flatten → (B, 120). Then `Linear(120, d_cross=32)`.
   - Option B (low-rank bilinear, smaller params): `cate_proj = Linear(15, r=8)(cate_heat)` → (B, 8); `time_proj = Linear(8, r=8)(time_context)` → (B, 8); `cross_8 = cate_proj * time_proj` → (B, 8) (Hadamard); then `Linear(8, d_cross=32)`.
   - **Use Option B** (low-rank bilinear) — fits the <5000 param cap better.
4. Output: `(B, 32)` dense vector

### Integration with I-643's PCVRHyFormer

In `model.py`'s `PCVRHyFormer.forward()`, after the existing `output = self.output_proj(all_q.view(B, -1))` (= I-643 path):

```python
# I-671: cate × time cross branch, gamma-gated at 0 for zero-init identity
cate_heat = inputs.item_dense_feats  # already shape (B, 15) per I-643 schema
time_context = self._extract_time_context(inputs)  # (B, 8), method above

cross_out = self.cate_time_cross(cate_heat, time_context)  # (B, 32)
# Map 32-dim cross_out to d_model=64 for fusion
cross_64 = self.cross_to_model(cross_out)  # (B, 64) — Linear(32, 64), ~2048 params

# Fusion: zero-gated residual
output = output + self.gamma_cross * cross_64
```

Add `gamma_cross = nn.Parameter(torch.tensor(0.0))` — same zero-init trick as I-670. At step 0, output = base = I-643. Gradient drives `gamma_cross` up if cross helps.
