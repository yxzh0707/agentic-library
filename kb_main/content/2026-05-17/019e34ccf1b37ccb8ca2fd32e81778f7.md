# TAAC x KDD Cup 2026 System Design v2

Last updated: 2026-04-11

## 1. Purpose

This document defines a practical v2 operating system for the TAAC x KDD Cup 2026 project under the current reality:

1. Round 1 starts on 2026-04-24.
2. The current local data scale is only 1000 samples.
3. The most important missing piece is not another model idea, but an experiment loop that can run without manual session babysitting.
4. Claude Code is the expensive brain. Codex is the cheaper hands.

The design goal is not "fully autonomous AGI lab". The goal is a tight, cheap, inspectable loop that can keep architecture exploration moving for the next 2 weeks.

## 2. Current Diagnosis

### 2.1 What already exists

The current repo already has the right primitives:

- `CLAUDE.md`: identity, decision protocol, session protocol, loop detection hints, and knowledge update rules.
- `manifest.json`: experiment ledger with core fields and current best baseline.
- `decision_log.md`: chronological reasoning trace.
- `docs/current_strategy.md`: current strategic direction.
- `docs/domain_hints.md`: hard constraints, strong priors, and local findings.
- `docs/experiment_strategy.md`: ablation logic and 1000-sample warnings.

### 2.2 What is missing

The system is still not closed-loop:

1. Experiment execution is manual.
2. Post-experiment analysis exists as prose rules, not as a callable loop controller.
3. QA mostly targets experiment correctness, but not agent behavior.
4. 1000-sample experiments can easily drift into fake optimization instead of architecture ranking.
5. Claude/Codex division exists conceptually, but there is no compressed handoff contract.

## 3. Design Principles

### 3.1 Closed loop first

The core loop must be:

`run experiment -> summarize result -> compare with strategy/priors -> choose next action -> dispatch next experiment`

No human should need to start a new session every round unless a circuit breaker fires.

### 3.2 Agent behavior is auditable

QA should answer:

1. Did the agent follow protocol?
2. Did it update the right files?
3. Did it repeat itself?
4. Did it violate decision boundaries?
5. Did it drift away from current strategy?

### 3.3 1000-sample stage is for ranking directions, not chasing score

At this stage, the question is:

"Which architecture family survives small-scale testing with stable relative advantage?"

It is not:

"Can we squeeze another 0.001 AUC from learning rate, dropout, or seed?"

### 3.4 Expensive thinking is centralized

Claude should only do:

- strategic decisions
- protocol audit
- knowledge judgment
- compressed review

Codex should do:

- code generation
- file updates
- repetitive bookkeeping
- doc writing
- experiment launch plumbing

## 4. Proposed Closed-Loop Architecture

### 4.1 High-level components

The v2 loop uses six lightweight layers:

1. `L0 Runner`
   Runs train/eval/search commands and writes structured outputs.
2. `L0 Result QA`
   Checks whether the run finished, metrics were parsed, artifacts exist, and manifest can be updated safely.
3. `L1 Loop Controller`
   Reads repo state and decides the next step using fixed rules plus limited model judgment.
4. `L1 Agent QA`
   Audits whether the agent followed session and decision protocol.
5. `L2 Orchestrator`
   Claude reviews only a compressed context packet when needed.
6. `Executor`
   Codex performs file edits, config generation, logging, and batch operations.

### 4.2 Recommended implementation choice

Use a local shell loop as the default control plane, not Claude `/loop` as the primary path.

Reason:

1. Shell loop is transparent and easy to debug.
2. It can run even when model context is unavailable.
3. It gives explicit control over retry count, cooldown, and stop conditions.
4. Claude `/loop` can remain an optional convenience wrapper, not the foundational mechanism.

Recommended default:

- Windows PowerShell script: `scripts/experiment_loop.ps1`
- Optional per-iteration Codex call: `codex exec ...`
- Optional escalation to Claude only on strategic fork, ASK action, or QA failure

## 5. End-to-End Loop Flow

### 5.1 Single iteration flow

Each loop iteration should execute the following steps:

1. Load state
   Read `manifest.json`, `decision_log.md`, `docs/current_strategy.md`, `docs/domain_hints.md`, and `docs/operating_context.md`.
2. Build compressed context packet
   Extract only:
   - current phase
   - best experiment
   - last 3 experiments
   - current strategy summary
   - top hard constraints
   - active strong priors
   - open questions
   - current architecture frontier
3. Choose next action
   The loop controller classifies the next step as one of:
   - `run_architecture_variant`
   - `run_reproduction`
   - `run_simplification_ablation`
   - `run_scale_test`
   - `analyze_failure`
   - `ask_human`
   - `stop`
4. Generate or select config
   Usually delegated to Codex. Output is a new config package or config patch.
5. Run experiment
   Launch `taac-train` or related vendor command.
6. Parse result
   Convert raw logs into a small JSON summary.
7. Update ledgers
   Update `manifest.json`, append to `decision_log.md`, and update operating-context files if new knowledge emerged.
8. Run agent QA
   Validate protocol compliance and loop quality.
9. Evaluate circuit breaker
   If a stop condition is met, halt and emit a concise report.
10. Start next iteration automatically
   If safe, loop continues without human input.

### 5.2 Suggested file outputs per iteration

Each experiment iteration should produce:

- `artifacts/runs/<exp_id>/metrics.json`
- `artifacts/runs/<exp_id>/summary.md`
- `artifacts/runs/<exp_id>/qa.json`
- `artifacts/runs/<exp_id>/agent_audit.json`

This is enough. Do not overbuild a full database.

## 6. Loop Controller Logic

### 6.1 Core decision philosophy

During the 1000-sample phase, the controller should prefer decisions in this order:

1. Distinguish architecture families.
2. Verify whether a gain is robust enough to matter.
3. Remove complexity that does not justify itself.
4. Only then consider minor optimization.

If the system cannot tell whether a gain came from architecture or noise, it should not continue HPO. It should run a discriminating ablation instead.

### 6.2 Decision inputs

The controller should read:

- `manifest.json`
  Used for trend, duplication, and best-known baseline.
- `docs/domain_hints.md`
  Used for constraints, strong priors, and contradiction checks.
- `docs/current_strategy.md`
  Used to reject off-strategy ideas.
- `docs/operating_context.md`
  Used for current open hypotheses and loop state.
- `decision_log.md`
  Used only for the latest recent decisions, not full replay.

### 6.3 Suggested next-step rules

Use rules before using model judgment:

1. If the last run failed, do not launch a new architecture branch immediately.
   Run `analyze_failure`.
2. If the last 2 completed runs changed more than one major variable at once, do not continue.
   Force a simpler ablation.
3. If a run shows less than `+0.0015` AUC over baseline on 1000 samples and increases complexity, do not branch from it yet.
   Mark as weak evidence.
4. If a run contradicts a strong prior, require one reproduction or simplification test before updating the prior.
5. If a candidate direction beats baseline and also survives one simplification or reproduction test, prioritize that architecture family in the next iteration.
6. If the recent run is only a training trick or HPO tweak while architecture ranking is still unresolved, deprioritize it.

### 6.4 Architecture-first action ladder

The action ladder should be:

1. Baseline reproduction
2. Single-component architecture delta
3. Simplification ablation
4. Small scale test
5. Interaction test
6. Training trick
7. Micro-HPO

The loop should not move to step 6 or 7 unless there is a current architecture winner candidate.

## 7. Circuit Breakers

### 7.1 Mandatory stop conditions

The loop must stop automatically if any of the following happens:

1. `3` consecutive completed experiments with no meaningful improvement.
   Suggested threshold: no improvement over best AUC by `>= 0.0015`.
2. `2` consecutive identical or near-identical failed runs with the same root cause.
3. `8` total experiments in one unattended loop session.
4. Agent QA score below threshold for `2` consecutive iterations.
5. The next proposed action is `ASK` per `CLAUDE.md`.
6. The proposed experiment clearly violates `docs/current_strategy.md` or a hard constraint.
7. Required files are stale, missing, or inconsistent:
   - manifest not updated
   - decision log missing latest session entry
   - operating context not refreshed after knowledge change

### 7.2 Soft pause conditions

The loop should pause and request higher-level review if:

1. One direction appears promising but evidence is noisy.
2. A result refutes a strong prior from papers.
3. A model improves AUC but likely violates latency assumptions.
4. There is a strategic fork between `OneTrans-style stabilization` and `HyFormer-style migration`.

## 8. Agent QA: Behavior Supervision

### 8.1 Scope

This QA layer does not judge whether the metric itself is mathematically correct. That is L0 result QA.

This layer judges the agent.

### 8.2 What must be checked

Each iteration must audit these five dimensions:

1. Session protocol compliance
   Did the agent read the required files before deciding?
2. Decision protocol compliance
   Did it perform an `ASK`-class action without escalation?
3. Loop quality
   Is it repeating low-information experiments?
4. State bookkeeping
   Did it correctly update `manifest.json`, `decision_log.md`, and context files?
5. Strategy alignment
   Is the action consistent with `docs/current_strategy.md`?

### 8.3 Lightweight self-check checklist

At the end of every iteration, the acting agent writes a compact checklist to `artifacts/runs/<exp_id>/agent_audit.json`.

Suggested schema:

```json
{
  "exp_id": "exp_20260411_xxx",
  "read_required_files": {
    "manifest": true,
    "decision_log": true,
    "current_strategy": true,
    "domain_hints": true,
    "operating_context": true
  },
  "decision_protocol": {
    "action_class": "SAFE",
    "requires_ask": false,
    "escalated": false
  },
  "loop_quality": {
    "duplicate_of_recent": false,
    "changed_major_axes_count": 1,
    "architecture_first": true
  },
  "bookkeeping": {
    "manifest_updated": true,
    "decision_log_updated": true,
    "operating_context_updated": false
  },
  "strategy_alignment": {
    "aligned": true,
    "reason": "single-component architecture ablation within HyFormer-style direction"
  },
  "qa_score": 0.92,
  "issues": []
}
```

This should be rule-generated as much as possible. Do not spend large model context on it.

### 8.4 Reviewer mode

Add a cheap periodic reviewer every `3` iterations, not every iteration.

Recommended implementation:

- A small Codex review step over:
  - last 3 entries in `manifest.json`
  - last 3 decision summaries
  - current strategy summary
  - latest agent audit files

Output:

- `docs/reviewer_notes.md` append-only section
- a single verdict:
  - `continue`
  - `continue_with_warning`
  - `pause_for_claude_review`

This is enough. Do not create a second expensive autonomous agent swarm.

### 8.5 Loop detection rules

Flag an iteration if any of the following is true:

1. Same parent experiment and same major hypothesis were tried twice with only cosmetic config changes.
2. More than `2` major variables changed in one run.
3. The last `3` runs are all training-trick or HPO variants while architecture frontier is still unresolved.
4. An experiment repeats a previously failed root cause without a documented fix.
5. A new run is not clearly traceable to an open hypothesis in `operating_context.md`.

## 9. 1000-Sample Strategy

### 9.1 Correct objective

Under 1000 samples, the metric objective is:

`stable relative ranking of architecture directions`

Not:

`maximize absolute AUC`

This means the loop controller should ask:

1. Does direction A consistently dominate direction B under the same protocol?
2. Does a simplification keep the gain?
3. Does the gain survive seed or split noise enough to justify further investment?

### 9.2 Practical decision policy

Use the following buckets:

1. `Promising`
   Beats baseline by a meaningful margin and survives one confirmation check.
2. `Weak signal`
   Slight improvement, but likely noise or confounded by too many changes.
3. `Dead end`
   Degrades clearly, violates latency intuition, or fails simplification.
4. `Unresolved`
   Evidence too noisy; requires a discriminating follow-up experiment.

The loop should optimize for moving experiments into one of these buckets quickly.

### 9.3 What the loop should prioritize

Priority order for the current phase:

1. Lock baseline reproducibility.
2. Compare `OneTrans-stabilized` vs `HyFormer-style hybrid blocks`.
3. Test one component at a time:
   - tokenizer choice
   - sequence/non-sequence interaction pattern
   - normalization style
   - FFN sharing pattern
4. Run simplification tests on any positive result.
5. Track scale-up assumptions explicitly.

### 9.4 What the loop should avoid

Do not burn cycles on:

1. seed sweeping
2. learning-rate micro search
3. dropout tuning
4. tiny hidden-dim nudges
5. optimizer fiddling

Unless architecture ranking is already stable, these are noise-consuming actions.

## 10. Token Economy

### 10.1 Role split matrix

| Work item | Claude Code | Codex |
|---|---|---|
| Strategic branch selection | Primary | Support |
| ASK/NOTIFY review | Primary | No |
| Loop controller plumbing | Review only | Primary |
| Config generation | No | Primary |
| Bulk manifest and log maintenance | No | Primary |
| Result parsing and structured summaries | Review only | Primary |
| Agent QA self-check generation | No | Primary |
| Periodic audit review | Escalation only | Primary |
| Knowledge-base document drafting | Review only | Primary |
| Notion or external sync | No | Primary |

### 10.2 Compression rule

Claude should never receive raw full logs by default.

Instead the loop builds a compact context packet such as:

```json
{
  "phase": "baseline",
  "strategy": "architecture exploration on 1000-sample local data",
  "best_exp": {
    "id": "exp_20260410_204800_onetrans_baseline",
    "auc": 0.6943
  },
  "recent_experiments": [
    {
      "id": "exp_x1",
      "parent": "exp_base",
      "hypothesis": "replace norm with GLN",
      "auc": 0.6958,
      "delta_vs_best": 0.0015,
      "status": "completed",
      "verdict": "weak_signal"
    }
  ],
  "active_priors": [
    "start from vendor baseline",
    "architecture before HPO"
  ],
  "open_questions": [
    "Does hybrid block beat stabilized OneTrans?"
  ],
  "escalation_reason": "proposed next action changes architecture family"
}
```

This packet should stay under roughly `1-2 KB` whenever possible.

### 10.3 When Claude must be called

Escalate to Claude only when:

1. action class is `ASK`
2. agent QA fails twice
3. a strong prior is being overturned
4. a strategic branch must be chosen
5. loop reaches a circuit breaker but has multiple plausible next directions

Everything else should remain in the Codex lane.

## 11. Knowledge Base: Two-Layer Structure

### 11.1 Problem with the current state

Right now the repo has useful knowledge, but it is spread across strategy prose, domain hints, and decision logs. The loop needs one operational layer that is cheap to read every time.

### 11.2 Proposed two-layer design

#### Layer A: Operating layer

Create `docs/operating_context.md`.

This file is short and loop-oriented. It should answer:

1. What phase are we in now?
2. What are the top 3 architecture questions?
3. What is the current winner candidate?
4. What are the active stop rules?
5. What experiments are queued next?
6. What assumptions must be revalidated on full data?

Suggested sections:

- Current Phase
- Current Frontier
- Open Hypotheses
- Next 3 Experiments
- Active Circuit Breakers
- Scale-Up Assumptions
- Pending Human Decisions

This file is for fast read and decision.

#### Layer B: Evidence layer

The evidence layer remains append-heavy:

- `manifest.json`
- `decision_log.md`
- `docs/domain_hints.md`
- `docs/paper_analysis.md`
- `artifacts/runs/<exp_id>/summary.md`

This layer stores why the operating layer says what it says.

### 11.3 Update rule

Per experiment:

1. `manifest.json` always updates.
2. `decision_log.md` always appends.
3. `docs/operating_context.md` updates only if frontier, queue, or assumptions changed.
4. `docs/domain_hints.md` updates only if a finding becomes reusable knowledge or refutes a prior.

This keeps the hot path cheap.

## 12. Prior Consensus to Preserve

The v2 design should explicitly preserve the points already agreed in the previous round of discussion.

### 12.1 L0 QA script stays

L0 QA remains a script-level result validator. It should:

1. verify command success/failure
2. parse metrics
3. check artifact existence
4. detect malformed or partial outputs
5. block manifest update on invalid run state

This is not the same as agent QA.

### 12.2 Agent contract format stays structured

Agent I/O should stay structured and minimal.

Recommended contract packet:

```json
{
  "task_type": "run_architecture_variant",
  "context_packet_ref": "artifacts/context/latest_context.json",
  "hypothesis": "hybrid block improves seq/non-seq fusion over OneTrans baseline",
  "parent_experiment": "exp_20260410_204800_onetrans_baseline",
  "allowed_actions": ["config_edit", "train", "evaluate", "update_manifest", "append_decision_log"],
  "forbidden_actions": ["delete_results", "change_tokenization_family_without_ask"],
  "expected_outputs": [
    "config package",
    "metrics.json",
    "summary.md",
    "agent_audit.json"
  ]
}
```

### 12.3 Event-driven retrieval stays

Do not load all knowledge every time.

Retrieve context by event:

1. New experiment decision
   Read operating layer + last 3 experiments.
2. Prior contradiction
   Read relevant section of `domain_hints.md` + recent evidence.
3. Architecture branch choice
   Read `current_strategy.md`, operating layer, and relevant paper notes.
4. Error recurrence
   Read recent failure entries only.

This keeps token burn under control.

## 14. Minimal Loop Pseudocode

```powershell
$maxIterations = 8
$noImproveCount = 0
$errorCount = 0

for ($i = 1; $i -le $maxIterations; $i++) {
    python scripts/build_context_packet.py

    codex exec "
    Read artifacts/context/latest_context.json and decide next SAFE action.
    If action is ASK, output ASK and stop.
    Generate config or run instruction, then update planned outputs."

    if ($LASTEXITCODE -ne 0) {
        $errorCount += 1
        if ($errorCount -ge 2) { break }
        continue
    }

    powershell -File scripts/run_experiment.ps1
    python scripts/update_manifest.py
    python scripts/agent_self_check.py

    $decision = python scripts/reviewer_audit.py

    if ($decision -eq "pause_for_claude_review") { break }
    if (Test-NoImprovementThresholdReached) { break }
    if (Test-AskRequired) { break }
}
```

The real implementation can stay this simple. Do not introduce message queues, databases, or service orchestration.

## 16. Final Recommendation

The correct v2 system is a shell-driven closed loop with:

1. `manifest/domain_hints/current_strategy/operating_context` as the decision substrate
2. Codex doing the repetitive execution work
3. Claude only reviewing compressed strategic packets
4. explicit circuit breakers
5. a lightweight agent QA layer focused on protocol compliance and loop quality

The key question is not "Can the agent run forever?"

The key question is: "Can it cheaply produce better architecture decisions than a manually babysat workflow before 2026-04-24?"

This design is sufficient for that goal.
