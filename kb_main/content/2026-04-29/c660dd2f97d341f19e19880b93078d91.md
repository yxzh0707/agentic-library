# HyFormer — OneTrans 的最直接竞争者，给出"层间交替"的另一种解法

> arxiv 2601.12681 | 抖音搜索（字节）| 2026

## 它跟 OneTrans 的关系
两篇都是字节做的、都声称"unified backbone for sequence + feature interaction"，但走的路完全不同。**赛题选哪条路是核心决策**。

## HyFormer 的两个核心模块

### Query Decoding（NS → 长序列）
- 把非序列特征向量 F1...Fm 与序列池化摘要拼接
- 通过轻量级投影生成 N 个 **Global Query Tokens**
- 用这些 query token 对长序列的逐层 KV 做 multi-head cross-attention
- 直觉：让"全局非序列信号"主动去 attend 长行为序列，而不是把序列也当成 token 平等参与

### Query Boosting（NS 间交互）
- 把每个 query token 拆成 T 个通道子空间
- 跨 token 位置聚合对应子空间（类似 MLP-Mixer 的 token mixing）
- 再用逐 token FFN 细化 + 残差

每层先 Query Decoding 再 Query Boosting，反复堆叠。

## 跟 OneTrans 的本质差异

| 维度 | OneTrans | HyFormer |
|---|---|---|
| 序列与非序列的关系 | 都是 token，进同一 self-attention 流（区别只在参数共享规则）| 序列被压缩进 Global Tokens，token 间交互全在 NS 侧 |
| 块内交互 | 标准 MHA | Cross-attention + MLP-Mixer 风格 token mixing |
| 信息流 | 单向（causal）| 层间交替双向 |
| 长序列处理 | 靠 cross-request KV cache | 靠 Query Decoding 的池化压缩 |

OneTrans 的 framing 是"统一 token 池"，HyFormer 的 framing 是"全局 query 主动检索长序列"——这两个 framing 都合赛题"同构 backbone"的字面要求，但对延迟的影响不同。

## 实验数字
- 数据：抖音搜索 3B 样本 / 70 天 / 三条序列（长期搜索 + 搜索 Top-50 + 推荐流 Top-50）
- baseline AUC：LONGER+RankMixer 0.6478，MTGR/OneTrans ~0.648
- HyFormer：**AUC 0.6489 (+0.17%)**，FLOPs 3.9×10^12

字节自己人比下来，HyFormer 比 OneTrans 略高 ——但都在 0.001 的小数位竞争。这说明：**赛题里能拉开差距的是工程实现而非架构选型**。

## 我对赛题的 framing
- 如果走 OneTrans 风：精力花在 token 化规则 + KV cache，模型简单但工程要求高
- 如果走 HyFormer 风：精力花在 Query Decoding 的池化策略 + token mixing 内部维度切分，模型复杂但延迟天然有压缩
- **混合可能性**：用 OneTrans 的 NS 独占参数规则 + HyFormer 的 Query Decoding 当层间池化算子，这是潜在的 Unified Block Innovation 论文方向
