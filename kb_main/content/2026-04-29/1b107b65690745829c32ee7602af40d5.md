# 延迟工程线 — 赛题的隐藏 boss

赛题文档明确：**推理超时直接作废，同分按延迟升序排名**。这意味着延迟不是优化项，是淘汰线 + 排名打破规则。

## 三类延迟杠杆，按收益从大到小

### 1. 计算复杂度 — 选对 block
- 标准 self-attention: O(N^2 d)
- HSTU 的 spatial aggregation: 实测比 FlashAttention2 快 5.3x ~ 15.2x（8192 序列长度上）
- TokenMixer (RankMixer) / MLP-Mixer 风格: O(N d^2)，对小 N 大 d 比 attention 划算
- FM stacking (Wukong): 双线性，避开 attention 复杂度但表达力依赖深度

赛题预算下，HSTU/TokenMixer 是默认选择，纯 self-attention 的容量预算会少 5-15x。

### 2. 请求结构 — Cross-request KV Cache
赛题样本是 (用户, 上下文, 目标广告)。一次用户请求里要打分多个候选广告，但用户的序列是同一个。
- 标准做法：每个 (user, candidate) 对独立前向 → 序列侧重复算
- OneTrans 做法：序列侧算一次，KV 缓存；每个 candidate 只算自己的 NS token + cross-attention
- 收益：runtime -30%, memory -50%（OneTrans 论文实测）

这是赛题里**几乎免费的延迟收益**，因为不影响离线 AUC。

### 3. 内核与精度 — FlashAttention / FlashInfer / 混合精度
- FlashAttention-2 已经是 baseline 必须有的
- FlashInfer 在 LLM serving 上比 compiler 后端 ITL 减少 29-69%（推荐域类似可借鉴）
- BF16/FP16 混合精度训练 + 推理是常规
- Activation recomputation：训练时省显存，间接让模型可以更大

## 延迟相关常见误区（赛题里要避开）

### 误区 A：以为模型小就一定快
不一定。一个 4 层 64 维的标准 Transformer，因为 attention 的 O(N^2) 在长序列下可能比 8 层 128 维的 HSTU 还慢。block 类型选择 > 层数压缩。

### 误区 B：以为推理优化和训练分开
不分开。如果训练用 full attention，推理换 cross-request KV cache 会破坏 attention pattern；要么训练时就用 causal + 两阶段切分（OneTrans 路线），要么训练就是 HyFormer 的 Query Decoding。

### 误区 C：把延迟优化留到最后
赛题"超时直接作废"是断崖式 punish，应该**先把延迟预算塞满，再把剩下的容量用来加 W/D/L**。即先做延迟测试，再决定模型大小，而不是反过来。

## 赛题专属的延迟决策树
```
样本进来：
├── 序列侧（4 个 domain，长度 N）
│   └── 同一 user 多 candidate？是 → KV cache 必须开
│   └── 长度 N > 1000？是 → HSTU 替 attention，或 GSU 风检索
└── 非序列侧（70 列字段）
    └── 多少 token？多 → token-specific 参数贵 → 考虑 group-wise + 共享子集
    └── dense 特征（10 列 user_dense）单独投影 vs 拼进 int 通道：影响内存带宽
```

## 工程估算（粗略）
- HuggingFace demo_1000.parquet 是 1k 样本，120 列。完整训练集量级估计 1B+。
- 单样本推理预算如果是 5ms，HSTU 4 层 128 维大概在 1-2ms 区间，留 60-70% 给 NS 侧和 IO。
- 若引入 cross-request KV cache，序列侧的 1-2ms 在每个 candidate 上摊薄到 0.1-0.3ms（按一次请求 10 candidate 估）。
