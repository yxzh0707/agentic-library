# 赛题 baseline (DeepContextNet) 拆解

> github.com/suyanli220/TAAC-2026-Baseline-Tencent-Advertisement-Contest

## 这个 baseline 是起跑线，任何提交都先跟它比

## 架构四阶段

1. **统一嵌入层**：稀疏类别 ID + 稠密向量映射到共享 d 维潜空间
2. **序列合成**：`Item_ID + Action_Type + Temporal_Bucket` 三个 embedding **加法融合**成一个事件 token
3. **深度交互**：多个 HSTU 块 + Rotary positional bias，处理 `[CLS, User, Item, Sequence]` token
4. **投影头**：非线性瓶颈层 → CTR 概率

## 关键 trick

| 技术 | 作用 |
|---|---|
| **全局 CLS 集成** | CLS token 聚合 user 静态属性 + item 特征 + 行为序列，做最终预测 |
| **时间感知衰减** | 对数时间分桶捕获新近性 |
| **混合精度训练** | torch.cuda.amp，省显存 |
| **Muon 优化器** | SVD 基础正交化梯度更新（这是个不太常见的 optimizer，值得查它的来源） |

## 默认超参（起点）
```
HIDDEN_DIM:    128
BLOCK_DEPTH:   4
LEARNING_RATE: 2e-4
SESSION_GAP:   1800 秒（用户行为切分阈值）
```

## 这个 baseline 暴露的三个改进口子

### 1. 序列合成是简单加法
`Item_ID + Action_Type + Temporal_Bucket` 加一起 → 一个 token。这把三个语义不同的信号压缩成同一向量。
**改进方向**：拼接 + 投影、各 emb 占独立维度切片、或像 HSTU 那样三个 sub-channel。

### 2. 非序列特征只占两个 token (User / Item)
赛题有 70 列非序列特征，baseline 把它们全压成两个 token，相当于早早做了大池化。
**改进方向**：按 OneTrans 的 group-wise tokenizer，让 user/item/cross 各分多个 token，给统一 block 更多 NS 端可玩的信号。

### 3. CLS 是唯一的预测出口
单 CLS 在多类 token 混合时容易被序列侧主导。
**改进方向**：candidate item token 自己也参与最终预测（target-aware），跟 CLS 联合输出。

## 直接可以做的对照实验

baseline 已就位的前提下，按代价从低到高排：
1. 加 Group-Layer Normalization（MTGR）— 几行代码
2. 把 NS 端从 2 token 扩到 8-16 token（OneTrans group-wise）— 改 tokenizer
3. NS 端用 token-specific 参数（OneTrans NS 独占规则）— 改 block 内层
4. 引入 cross-request KV cache（OneTrans）— 改 serving，离线 AUC 不变但延迟降，对应赛题第二指标

每一步都对应一篇论文里的具体 trick，验证目标是相同 FLOPs 下 AUC 增益。
