## 一、framing 翻转：v1.3+layered → v1.4 working_set

### 1.1 背景

`docs/clustering_pipeline.md` 描述的"层级聚类 + 双层 LLM 介入"是 v1.3 之后的第一次 framing 升级（2026-04-29~30）。把 21 个同项目文档形成 4 个并列 cluster + 1 个父簇。

实战中暴露问题：用户期望 22 个 TAAC 推荐赛题文档应该形成**一个大簇**（因为都是同一个项目衍生出来的），而不是被强制细分。

### 1.2 framing 翻转的核心

| 维度 | v1.3+layered（之前） | v1.4 working_set（现在） |
|---|---|---|
| cluster 语义 | 细粒度主题分组 | **项目 / 语境单元（working set）** |
| 子主题表达 | 拆成多个并列 cluster + parent_cluster_id 父簇 | **不拆 cluster**，子主题通过 `hub_role=center` anchor 在 working_set 内部呈现（前端 sub-hub） |
| cold_start LLM 任务 | "把文档分成 K 个簇" | "判断这堆文档来自几个 working set；每个 working set 内识别 1-5 个 sub-theme anchor" |
| K=1 输出 | 隐性歧视（mega-cluster 检查会 reject） | **常态**，鼓励 |
| `parent_cluster_id` 角色 | 把多个细簇 collapse 到父项目 | 保留但罕用 — 处理"多个独立 working set 共享更外层语境" |

### 1.3 实战效果

**测试数据**：22 个 TAAC 2026 推荐赛题文档（混 1 个 smoke 测试 placeholder）

| 路径 | 结果 |
|---|---|
| v1.3+layered cold_start | K=7 主题簇：「赛题元层」「统一架构」「Scaling Law」「序列建模」「工程实战」「作战计划」「验证边缘」+ 后续 hierarchy 加 1 个父簇 |
| v1.4 working_set cold_start | **K=2**：cluster 13「TAAC 2026 推荐赛题」(21 节点) + cluster 14「布局验证」(1 节点 smoke)；cluster 13 内有 5 个 LLM 推荐 sub_theme anchor + 9 个 on_ingest 已 center 节点，共 12 个 sub-hub |

后者跟用户期望吻合：一个 working set 就是一个 cluster。

## 二、已落地的代码改动

### 2.1 `coldStartCluster` 两阶段（`packages/core/src/clustering/clustering.ts`）

**Prompt 输出格式**：

```json
{
  "working_sets": [
    {
      "label": "<2-8 汉字的项目名>",
      "reasoning": "<为什么这些文档同属一个 working set>",
      "member_uuids": ["uuid1", ...],
      "sub_themes": [
        { "label": "<子主题>", "anchor_uuid": "<member 中的 uuid>" }
      ]
    }
  ]
}
```

**Prompt 关键句**（防止 v1.3+layered 时代的"细分压力"复发）：

> "如果所有文档其实属于同一个项目或同一个语境,正确答案就是 1 个 working set,不要强行细分。"

> "子主题不通过拆分 working set 表达,而是通过 sub_themes 列表里的 anchor_uuid 标记每个子主题的代表节点。"

**Validation 改造**：

- 不再有 mega-cluster reject（`maxSize > ceil(N/2)` 跟新 framing 直接冲突，已删）
- retry 2 次 → **4 次**，每次失败把具体原因塞回 prompt（`上一次输出有问题: {lastIssue}。请修正后重新输出。`），实战中显著降低假阴性
- 数据约束：所有 uuid 恰好出现一次；sub_theme.anchor_uuid 必须在所属 working_set 内

**持久化（Stage 2）**：

- per working_set 建 1 个 cluster 行
- 对每个 sub_theme.anchor_uuid 调 `storage.setHubRole(uuid, 'center', 'librarian', reason, op_id, 'agent:librarian:cold_start')`（如果还不是 center）
- op_log 记录两类：`extract.cold_start_cluster` + `set_hub_role`（每个 sub-theme anchor 一条）

### 2.2 `fullRecluster` GC 顺序修复（`packages/core/src/clustering/clustering.ts`）

**之前的 bug**：

```
1. 函数开头 GC: 把无 active 成员的簇标 emptied
2. HDBSCAN 跑
3. 如果 HDBSCAN 全 noise → 触发"cold-start protection"返回早期
4. 节点 cluster_id 没被改写，但 cluster 已被标 emptied
5. 结果：节点指向 emptied 簇行，前端只看到剩余 active 簇
```

实战中这次踩到：22 个高度同质化的 TAAC 文档，HDBSCAN 全 noise，触发保护，但 4 个 emptied 簇下挂了 12 个节点。

**修复**：GC 从函数开头挪到 HDBSCAN 成功写完 cluster_id 之后。保护分支早早返回时不再做 GC，状态保持完全一致。

`UPSERT clusters` 那条 SQL 也加了 `status='active'` — 让历史曾经 emptied 但 HDBSCAN 重新挑中的 cluster_id 复活时 status 也回到 active。

### 2.3 Librarian 计数 bug（`packages/core/src/agents/librarian.ts:226`、`packages/core/src/synthesis/synthesis.ts:394`）

```ts
const r = await synthesis.generateClusterReview(...);
if ('rejected' in r) rejected++;  // ← bug
else generated++;
```

`r` 类型是 `GenerateOk | GateRejection`，**两种都含 `rejected` 字段**（`{rejected: false, node}` 或 `{rejected: true, reason}`），`'rejected' in r` 恒 true。后果：weekly 报告永远是 `+0/N`，掩盖了真实进展。

**修复**：改为 `if (r.rejected)`。

### 2.4 `hub_source` 细化（`packages/shared/src/types.ts` + `clustering.ts:recomputeHubs`）

**之前**：`'raw_explicit' | 'synthesis_calculated' | 'none'` — 只区分 hub 是 raw 还是 synthesis，**不区分**"LLM 推荐 vs 字典序兜底"

**现在**：导出 `HubSource` 类型：

| 值 | 含义 |
|---|---|
| `librarian_recommended` | cluster_review.hub_recommendation 选的（LLM 看了完整 cluster） |
| `raw_lexical_fallback` | hub_role=center 候选中 created_at 最早的 |
| `synthesis_calculated` | cluster 没 raw center，cluster_review synthesis 自身当 hub |
| `none` | 无合格 hub |
| `raw_explicit` | legacy 值，历史 row 兼容 |

实现上把 `targetHub` 从 `Map<number, string | null>` 改成 `Map<number, { uuid, source } | null>`，每个 hub 选举分支显式打 source 标签。

### 2.5 noise 救援前移到 weekly（`librarian.runOnReview`）

之前 `rescueNoiseNodes` 只在 monthly 跑。高摄入下 noise 节点要等 21 天才能被救。现在 weekly review 末尾也跑一次（cheap LLM 调用，每个 noise 节点单次 ~1.4K tokens）。

### 2.6 multi-center 检测语义改造（`librarian.runOnReview`）

**之前**：`COUNT(center) >= 3 → flag cluster_friction "应该 split"`

跟新 framing 直接冲突：一个 working set 内多个 sub-hub anchor 是设计预期（这次 cluster 13 有 12 个 center）。

**现在**：

```sql
center_count >= 4 AND center_count * 5 > member_count * 3
-- 即 center 数 ≥ 4 且 > 60% 成员
```

只有 center 主导 membership（暗示 cluster 实际混了多个 working set）才告警，否则放过。

### 2.7 清理

- 删除 `scripts/probe_coldstart.ts`（一次性诊断脚本）
- 删除 `scripts/apply_coldstart.ts`（功能已并入源码 cold_start v2）

## 五、待修但未落地的设计粗糙点

按预期收益排序：

### 5.1 加 `reset_and_recluster` admin tool

**问题**：现在 cold_start 只在 0 active cluster 时触发；用户/agent 想"重来"没有标准入口，只能直接 SQL 改库。

**建议**：在 `packages/core/src/tools/admin_tools.ts` 加一个工具，permission_tag=`admin`：

```ts
{
  name: 'reset_clusters_and_recluster',
  description: '清空所有 active cluster + 节点 cluster_id，重跑 coldStartCluster。破坏性。',
  parameters: { type: 'object', properties: { confirm: { type: 'boolean' } }, required: ['confirm'] },
  handler: async (args, ctx) => {
    if (!args.confirm) return { ok: false, reason: 'confirm=true required' };
    // SQL: UPDATE clusters SET status='emptied' ... ; UPDATE nodes SET cluster_id=NULL ...
    // 然后 await clustering.coldStartCluster()
    // op_log: 'extract' kind='reset_and_recluster'
  }
}
```

### 5.2 HDBSCAN 全 noise 时主动建议 cold_start replay

**问题**：`fullRecluster` 全 noise 保护现在是被动 — 保留现状就完事。但同质化数据每次跑都会触发。

**建议**：保护分支里如果发现 active cluster 数 << 期望（如 `< ceil(N/15)`），写一条 flag 到 `flag_queue.cluster_friction`：「N 节点形成 K 簇，同质化暗示需要 cold_start replay」。下次 weekly 接到这条 flag 主动调 `coldStartCluster`（先清状态）。

### 5.3 `op_log` 记录 fullRecluster 的 cluster status 变更

**问题**：现在 fullRecluster 把 cluster `status='emptied'` 是直接 SQL 改，op_log 没记录。无法 blame / undo。

**建议**：在 GC step 改成逐条 update 并写 op_log `op_type='archive'` 或新增 `op_type='cluster_status_change'`。

### 5.4 `cluster_review.move_out` 流向新 cluster

**问题**：当前 background pass 消费 `move_out` 提议时只能搬到现有 active cluster。如果 LLM 想说"这个节点应该独立成新 working set"没出口。

**建议**：扩展 `move_out` payload 支持 `target_cluster_id: number | 'new'`。`new` 时 background pass 调一个简化版 cold_start 仅对那个节点 + 其相似邻居。

### 5.5 `cluster_review` prompt 适配 working_set 视角

**问题**：现在 `buildClusterReviewPrompt` 是 v1.3 时期写的，prompt 里讲"对一个簇做结构性判断:它在讨论什么、成员是否合理、谁应该是 hub、内部是否有子结构"。"子结构"在 v1.4 是 sub-hub anchor，应该明确引导 LLM 推荐 sub-theme anchor 而不是 propose split。

**建议**：在 `packages/core/src/synthesis/prompts.ts` 的 `buildClusterReviewPrompt` 加段：

> 这个簇代表一个 working set。如果你看到内部有 sub-themes，**不要 propose split**；应该在 hub_recommendation 之外另起一个字段 `sub_theme_recommendations: [{label, anchor_uuid}]`，指出哪些节点应该被标 hub_role=center 作为子主题代表。

落库时 librarian 消费这个字段，调 setHubRole — 类似 cold_start 的 sub_theme anchor 机制，但发生在 review 阶段。

### 5.6 前端展示 working_set 视角

**问题**：前端 `GraphTab` / `NodesTab` 当前默认显示 cluster + 内部 sub-hub。在 v1.4 framing 下这是正确的，但 `parent_cluster_id`（v1.3+layered 时期的"父簇"）当前几乎用不到了，前端如果还按"父簇 > 子簇 > 节点"三层渲染，会出现父簇只有 1 个子簇的退化情况。

**建议**：扫一遍 `packages/frontend/src/panels/VisualizationPanel/`，确认 single-child 父簇不会渲染成多余的一层。

未深入排查，可能不是真问题。

## 六、`knowledge_base_v1.3_design.md` 中已过时的部分

以下条目的内容跟当前实现有出入。设计稿不修改（保留为历史），但接手时**以本文为准**：

### 6.1 §6.1 主聚类:UMAP 降维 + HDBSCAN

**过时点**：v1.3 假设 UMAP+HDBSCAN 是分簇主路径，cold_start_cluster（LLM 兜底）只是异常路径。

**现状**：对小 N（< 80）+ 高同质化场景，HDBSCAN 经常全 noise，`coldStartCluster`（v1.4 两阶段 working_set 版本）实际承担主分簇职责。HDBSCAN 主要作用是月度全量重聚 + 检测漂移。

### 6.2 §6.2 关键参数 — `hdbscan.min_cluster_size = 12`

**过时点**：硬编码 12，对 N < 96 时几乎必然全 noise。

**现状**：`adaptParamsForN(N)` 已实现自适应：`min(12, max(3, floor(N/8)))`。仍以 12 为名义默认。

### 6.3 §6.3 增量与全量 — 缺 30 天软锁 / cold_start 入口

**过时点**：v1.3 设计稿只描述 HDBSCAN，没提：
- 30 天软锁（fullRecluster 跑前查 op_log 'move' 操作排除 30 天内被 LLM/user 改过的节点）
- cold_start_cluster 是 weekly 的 0 → 1 簇路径
- rescueNoiseNodes 是 monthly + weekly 跑的 LLM 兜底

**现状**：完整流程见 `docs/clustering_pipeline.md` §二。

### 6.4 §6.5 子结构判定（k-means + silhouette）

**过时点**：v1.3 设计稿写"对簇内 e_l1 跑 k-means(k=2,3,4) 算 silhouette，>0.5 拆分"。

**现状**：从未实施。子结构表达从"拆 cluster"完全翻转为"sub-hub anchor"。

具体来说，v1.4 路径：

- cold_start 阶段：LLM 直接输出 sub_themes，落到 hub_role=center
- on_ingest 阶段：LLM 判断单文档是否 center
- weekly cluster_review 阶段：LLM 推荐 hub（这里也可以扩展 sub_theme，见 §5.5 待办）
- 前端：`computeSubclusterAnchors` 把 cluster 内非 hub 节点按 cosine 归到最近的 hub_role=center，渲染成绿色 sub_member

代码里 `detectSubstructure` 函数（`clustering.ts:487` 附近）还在，但只作为 diagnostic 接口暴露，不参与决策。

### 6.5 §6.7 Hub 计算

**过时点**：v1.3 设计稿写：

```
if 簇内有 raw 节点 hub_role.value == 'center':
  hub_uuid = 该 raw
  hub_source = 'raw_explicit'
elif 簇内有 cluster_review subtype synthesis 且 cluster_id == 当前簇:
  hub_uuid = 该 synthesis
  hub_source = 'synthesis_calculated'
else:
  hub_uuid = null
```

**现状**（见本文 §2.4）：增加了第 0 优先级 `cluster_review.hub_recommendation`（LLM 推荐），且 hub_source 不只表示 raw/synthesis，记录的是**决定 origin**。完整逻辑：

```
对每个 active cluster：
  优先级 0: cluster_review.hub_recommendation.proposed_hub_uuid
    → 验证该节点是 cluster 内的 active raw
    → 采纳，hub_source = 'librarian_recommended'
    → 如果该节点的 hub_role != 'center'，auto op_set_hub_role 升级到 center
  优先级 1: hub_role='center' 候选中 created_at 最早的 raw
    → hub_source = 'raw_lexical_fallback'
  优先级 2: cluster_review synthesis 自身
    → hub_source = 'synthesis_calculated'
  优先级 3: NULL
    → hub_source = 'none'
```

## 八、值得回看的 op_log 模式

排查"为什么聚类长这样"的时候直接看 op_log：

```sql
-- 最近 cold_start 形成的 working set
SELECT timestamp, args FROM op_log
WHERE op_type='extract' AND json_extract(args,'$.kind')='cold_start_cluster'
ORDER BY timestamp DESC LIMIT 5;

-- 谁被 LLM 升级为 sub-theme anchor
SELECT timestamp, json_extract(args,'$.uuid'), json_extract(args,'$.sub_theme'), reason
FROM op_log
WHERE op_type='set_hub_role' AND agent_id='system:cold_start'
ORDER BY timestamp DESC LIMIT 10;

-- cluster_review hub_recommendation 落地路径
SELECT timestamp, json_extract(args,'$.uuid'), json_extract(args,'$.cluster_id')
FROM op_log
WHERE op_type='set_hub_role' AND agent_id='system:hub_election'
ORDER BY timestamp DESC LIMIT 10;
```

**接手者注意事项**：

- 本次升级里 v1.4 working_set framing 是**全局假设**，不只是 cold_start 单点改造。任何后续聚类相关的 framing 讨论默认假设 cluster=working set。
- 不要回到 "cluster=细粒度主题，sub-theme=拆 cluster" 的 v1.3+layered 思路 — 这是用户明确反对的方向。
- `hub_role=center` 现在有两种来源（auto_detected on_ingest + librarian cold_start/cluster_review），都是合法 sub-hub anchor，前端展示一致。
- LLM 在 cold_start 阶段的输出方差较大（同 prompt 两次可能 K=1 vs K=3 mega），现版用 4 次 retry + feedback prompt 已基本稳定，但极端 case 还需要观察。
