# 长序列建模线：SIM / TWIN / TWIN V2 / TransAct / TransAct V2

赛题给的序列每域 9~14 列、是 list<int64>，单个用户的事件总量在哪个量级取决于 list 长度——但工业系统里这个数字常常是几千到几万。**长序列处理是赛题延迟约束下的关键工程点**。

## SIM — 阿里 2020，定义了"长序列 = 两阶段检索"范式

> arxiv 2006.05639

两个 cascaded search unit：
1. **General Search Unit (GSU)**：从原始任意长序列里，用候选 item 做 query，检索出相关子序列
2. **Exact Search Unit (ESU)**：在子序列上做精确建模

工业部署：阿里展示广告，CTR +7.1%、RPM +4.4%，**序列长度上限 54000**。

## TWIN — 快手 2023，把 GSU/ESU 用同一套参数

> arxiv 2302.02352

SIM 的问题：GSU 和 ESU 是不同模型，相关性 score 不一致。TWIN 让两者共享 attention 参数，在 GSU 里也用 ESU 同样的 target attention 公式。

## TWIN V2 — 快手 2024，scaling ultra-long

> arxiv 2407.16357

继续 push 到 lifelong 行为，重点解决长尾 item 在 GSU 里被检索不到的问题。

## TransAct — Pinterest 2023，实时短序列 + 离线 batch embedding 混合

> arxiv 2306.00248 | KDD 2023

混合架构：
- TransAct 在 serving 端实时跑 Transformer 处理近期行为
- 离线 batch 生成长期 user embedding
- 两者在 ranking 阶段融合

亮点：能区分 action_type 的 importance（对应赛题里 Domain A/B/C/D 的 action 区分）。在线 +11% engagement，非核心用户 +17%。

## TransAct V2 — Pinterest 2025，lifelong 化

> arxiv 2506.02267

三个新特性：
1. lifelong 长序列直接进 CTR
2. **Next Action Loss**：辅助 loss 预测下一个 action（生成式视角）
3. 低延迟部署方案

在线收益：+6.35% Repin、-12.80% Hide、+1.41% Time Spent。

## 这条线对赛题的启示

### 直接可复用
- **Action type embedding** 必须做（TransAct 已证明区分 action type 的重要性）
- **target-aware attention**（用候选广告做 query）—— SIM/TWIN 的核心
- **辅助 loss = next action prediction**（TransAct V2）—— 在赛题主目标 pCVR 之外加一个序列重建 loss，可能拉高 AUC 而不增加 serving 成本

### 框架级决策
赛题禁 ensemble，所以不能搞 "TransAct 风的离线 batch + 在线实时" 双塔。
**统一 backbone 路线下，长序列只能用：(a) HSTU 的 5x 加速 + 直接喂全长 (b) GSU 风的 retrieve-then-rank 内嵌进 backbone**。

(b) 这个方向有意思：把 GSU 当成一个**可微的 sparse attention**，用候选广告 token 当 query 检索出短序列，再 self-attention。这跟 OneTrans 的 cross-request KV cache 是正交的，可以叠加。

### 数字校准
SIM 的 54000 长度是上界。赛题序列实际长度估计在几百到几千 quan，没必要做 GSU——直接 HSTU 跑全长可能就够。先做 baseline 量一下序列长度分布再决定。
