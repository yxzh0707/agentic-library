# 工程实战三件套：蒸馏 / 多任务 CTR+CVR / Embedding 哈希

赛题禁 ensemble + 延迟约束 + 大词表，这三个工程问题压缩到下面三块技术。

## 一、知识蒸馏 — 禁 ensemble 下的"软合规"路径

### 为什么对赛题至关重要
赛题禁 ensemble，但**蒸馏不算 ensemble**——蒸馏的产出是单个学生模型，推理时只跑学生。这给了一条"训练阶段堆资源，推理阶段省成本"的合法路线。

### 三种用法（按对赛题适用度排序）

#### 用法 A — 大模型蒸成可上线的小模型
- 训练阶段跑一个 OneTrans-Large（不要求延迟达标）当 teacher
- 学生用 MTGR-Small（满足延迟），从 teacher 的 logit + 中间层蒸
- 学生最终提交，teacher 不上线
- 这是工业最常见的做法，Pinterest/Meta 论文都有报告

#### 用法 B — Multi-teacher 知识聚合到单学生
- 训练 N 个不同架构 teacher（一个 HSTU、一个 OneTrans、一个 HyFormer）
- 学生从所有 teacher 的 logit 平均蒸
- 等价于用蒸馏代替 ensemble 拿 ensemble 的精度
- **但要确认赛题规则**：multi-teacher 是否被视为变相 ensemble？这是合规风险

#### 用法 C — Self-distillation
- 同一模型先训一个完整版，再用它的 logit 当 soft target 重训
- 已知 +0.2~0.5% AUC 是常见收益
- 完全合规，最便宜的精度提升

### 关键参考
- "Bridging the Gap: Hidden Challenges in KD for Online Ranking Systems" (2408.14678) — 列出生产环境蒸馏的真实坑：teacher/student 数据分布漂移、teacher 配置搜索成本
- "A Unified KD and Semi-Supervised Learning Framework for Industrial Ads" (2502.06834)
- "Ranking Distillation" (KDD 2018, jiaxit) — 经典理论框架

### 实施要点
- 蒸馏温度 T：CTR/CVR 任务通常 T=2~4
- loss 加权：α·CE(y, student) + (1-α)·KL(teacher_logit/T, student_logit/T)，α 一般 0.3~0.5
- 中间层蒸馏（attention 矩阵 / hidden state）通常比单 logit 蒸更稳，但实现复杂

## 二、多任务 CTR + CVR 联合训练

### 数据分布的本质问题
- CVR 是 post-click 行为：sample selection bias —— 训练只用 click 后样本，serving 用全量
- CTR 在全空间上有标签，CVR 只有部分有

### ESMM (阿里 2018) — 整空间多任务
> arxiv 1804.07931

- 不直接预测 CVR，而是预测 CTR 和 CTCVR (= CTR × CVR)
- 用全空间样本训练（包括 click 失败的）
- CVR 从 CTR/CTCVR 比值反推
- 解决 sample selection bias 的事实标准

### PLE (Tencent 2020) — Progressive Layered Extraction
- 多任务里"任务相关性低"导致负迁移
- PLE 用 task-shared experts + task-specific experts，CGC (Customized Gate Control) 做任务路由
- 比 MMoE 更稳

### ESCM2 (2204.05125)
- 在 ESMM 上加 counterfactual risk minimizer 解决 IEB 和 PIP 偏差
- 阿里部署

### 赛题适用性
赛题主目标是 pCVR，但训练时多任务做 CTR + CVR 几乎一定会涨：
- ESMM 框架处理 sample bias
- PLE 风的 expert + gate 加在 unified backbone 顶层
- 注意：赛题数据 label_type 字段编码了什么细节决定了能不能直接套 ESMM

### 实施要点
- 不必把整个 ESMM/PLE 框架搬过来，**最小有用版本**：在 backbone 顶层加两个 head（CTR head + CVR head），loss 加权 0.3·CTR + 0.7·CVR
- 多任务比单任务通常 +0.3~1.0% AUC，几乎免费

## 三、Embedding 压缩 / Hashing — 大词表下的内存与冷启动

### 问题
赛题里 user_id / item_id 的基数动辄百万到亿。如果每个 ID 一个独立 d=128 的 embedding：
- 1B item × 128 × 4 bytes = 512 GB 显存
- 完全不可行，必须压缩

### 经典方案
- **Hashing trick**：ID → hash(ID) % B，B 个 bucket。简单但语义相似 item 会冲突
- **Multi-hash**：用 k 个不同 hash function，embedding = sum 或 concat 多个 hash 桶
- **Compositional embedding** (Q-R trick)：ID = (q, r)，分别 lookup quotient embedding 和 remainder embedding，组合
- **Learned hash** (2203.15837)：训练 hash function 让语义相似 ID 主动 collide

### Semantic ID — 当前最先进
- TIGER 把 item content embedding 用 RQ-VAE 量化成 (c1, c2, c3, c4) 离散 ID
- 结果：相似 item 共享前缀 → 共享底层 embedding → 冷启动天然好
- "Enhancing Embedding Representation Stability with Semantic ID" (2504.02137) 证明了在长期训练下比 random hash 稳定得多

### 赛题里的实施建议
- 不要早期就上复杂方案。**先 hash trick + bucket 64M-256M**，看显存够不够
- 如果不够：multi-hash 或 Q-R 分解
- 如果想冲创新分：semantic ID（但要先能从行为共现学出 item embedding）

## 三件套联合 framing
这三个看起来分离，**但在赛题里能合成一条流水线**：
1. 训练阶段：大 backbone（OneTrans-L）+ ESMM 多任务 → teacher
2. 蒸馏到小学生：MTGR-S + 同样的 multi-task heads
3. 学生用 semantic ID embedding 减少参数 + 增加冷启动鲁棒性

整条流水线的产物是单模型，符合赛题禁 ensemble 规则，但训练资源利用了多任务 + 大模型 + 高级 tokenization 的组合优势。
