# Sample Is Feature — 一个对赛题最有可能拿"创新分"的新 axis

> arxiv 2604.15650 | 2026

## 这篇为什么值得单独建一个节点
它是目前所有 unified 工作里**唯一在挑战"item-level token 假设"的**。如果赛题选手要在 Unified Block Innovation Award 上做出有论文价值的贡献，这篇是最近的对手 + 最近的肩膀。

## 它的核心观察

之前所有"sample information scaling"工作（HSTU/RankMixer/OneTrans）都默认：
- 一个 sample = 一段历史行为 + 当前 candidate
- 历史每个 item 编成一个 token
- 非序列特征编成一些 token
- backbone scaling = 增加 token 数 / 增加 W / 增加 D

**Sample Is Feature 指出两个结构性局限**：
1. 历史每个 item 只编了"行为发生了"这件事，**该 sample 当时的上下文（请求时间、用户 state、其他 candidate）都丢了**
2. 序列 token 和非序列 token 是异构的（前者是 event，后者是 attribute），强行用同一 backbone 处理是次优的

## 它的解法

引入 **sample-level token**：每个历史"sample"（不是每个 item）作为一个 token，编码这次 sample 的全部上下文。

直觉：
- 旧做法：只看用户点了什么（item 的 ID 序列）
- 新做法：看用户在什么样的请求场景下点了什么（context-aware 的 sample 序列）

## 跟赛题数据的契合度

赛题数据的形态非常适合这个 framing：
- 每个 sample = (user, context, candidate) 三元组
- 用户历史里也是这样的 sample 序列
- 但赛题给的 4 个 domain 序列只编了"行为侧"，没有显式给"当时的非序列 context"

**赛题数据隐含约束**：HuggingFace parquet 的列里 user/item/cross_feats 都是当前 sample 的，历史序列里**没有**当时的 user_feats 或 cross_feats——这意味着无法严格做 sample-level token。

但部分可以：
- 历史每个 item 编 (item_id, action_type, timestamp, **action_aggregated_context**)
- action_aggregated_context 用从行为共现里学到的伪 context（比如该 item 当时被多少人交互、当时哪个 domain 主导）
- 这就近似 sample-level token，比单纯 item-level 信号丰富

## 这给赛题创新方向的两个口子

### 口子 1 — 论文级：在赛题数据上重新形式化"sample-level token"
- 提出：在没有历史 context 的数据上，怎么用合理代理（如 timestamp 邻近 sample 的 candidate 池）构造 sample-level token
- 这是 paper 价值，跟 Sample Is Feature 形成对话

### 口子 2 — 工程级：把它纳入 token 化层级
- Token 层级：domain-token（最粗）→ sample-token（中）→ item-token（baseline 默认）
- 在 backbone 不同层用不同粒度的 token
- 类似 hierarchical attention 但 axis 是 sample 粒度而非空间

## 风险
- Sample-level token 会让序列变短（比如原来 100 个 item，可能压成 30 个 sample）
- 短序列 → attention 的 O(N²) 不再痛 → HSTU 的速度优势变小
- 整体延迟可能不降反升，**要做 ablation 确认**
